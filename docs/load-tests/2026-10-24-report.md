# Load test report: 24 October 2026 (production)

- **When:** Saturday 24 Oct 2026, about 12:00 to 13:15 UTC
- **Against:** production, `https://webinarliv.com`, edge (LL-HLS) webinars and one meeting
- **Kit:** `e2e/load/` ([docs/LOAD-TESTING.md](../LOAD-TESTING.md)), as merged in #712
- **Raw data:** the generator logs and `results.json` files from both generators (secrets, join keys and test-account passwords left out)

---

## 1. Executive summary

**What we proved.** One 4-core video box carried a full-size webinar:

- 2 presenters on stage, plus a screen share and a cloud recording
- 500 viewers at the same time, watching through the CDN. The server counted 525 at the peak, because 25 more viewers were running on the first generator.
- chat, questions, poll votes and joins running at the same time

**Joins.** Every viewer got in. The runs recorded about 1,480 viewer joins with client data, plus 300 more in one step whose client summary was lost. These were through the CDN and straight to the box. The only failures were 4 network errors in run 3, on an overloaded test machine; section 5 explains why that was the test machine, not the server.

**Delay.** Viewers saw the presenter about 3 to 4 seconds late at 500 viewers. With 50 to 200 viewers it was about 1.3 to 1.5 seconds.

**Server errors.** The API returned no 5xx errors in any run.

**How close we are to the limit.**

- The video box is near its ceiling. With the CDN in front and 500 viewers, the box ran at about 79% CPU.
- When the same 500 viewers went straight to the box (no CDN), it hit 97% CPU, which is saturated.
- So 500 viewers with recording and screen share on a 4-core box is about the maximum. To go past 500, or to add headroom, we need a bigger box or a second one.

**The CDN is essential, but it is not doing its whole job yet.** Without it, the box is saturated at 500 viewers. Even with it, the box still sent out about 451 Mbit/s. Direct to the box it sent about 566 Mbit/s. So the CDN took only about a fifth of the traffic off the box. We should check the CDN's cache settings for the live stream before a big event.

**The real fragility is the database connection pool, not video.** After the test, two routine API deploys failed. The new servers could not get database connections: the pool allows 15 connections, and the 3 running servers already use all 15. Customers saw nothing, because production stayed on the previous version. But the same limit could stop the API from scaling up during a large live event. This has to be fixed before any big event. A fix is in progress.

**Some numbers in this test are effects of the test machines, not real problems.** Our test machines were 4-core droplets, because DigitalOcean refused the 8-core size for our account tier. They ran out of CPU at about 200 simulated viewers each. Most of the "stalls" (short buffering events) counted at 500 viewers come from the test machines, though not all of them (see section 5).

**Small meetings work.**

- A meeting of a host plus 9 attendees connected everyone, with 0% packet loss.
- The freezes at 9 attendees came from running 9 Chrome tabs on one 4-core test machine.

**Next steps, in priority order:**

1. Fix database pooling.
2. Get DigitalOcean to raise our account tier, so we can use larger test machines and video boxes.
3. Decide on a bigger box, or a second box, for events above 500 viewers or with recording.
4. Check the CDN's caching.
5. Repeat the test at 1,000 viewers with 3 or more test machines.

## 2. Setup and method

### 2.1 System under test

| Part | What it was |
|---|---|
| Video box | On-demand DigitalOcean `c-4` (4 vCPU) in BLR1. It runs:<br>- LiveKit SFU (presenters)<br>- MediaMTX LL-HLS origin<br>- the mix compositor (edge delivery)<br>- the cloud recorder<br>It was cold at the start of run 1 and started on demand. |
| CDN | Bunny pull zone in front of the origin for viewers (the default playback URL from `/join`) |
| API | Go service on Cloud Run, `maxScale` 3 (concurrency 500 per instance) |
| Database | Supabase Postgres through the **session** pooler, `pool_size` 15 |
| Stream | LL-HLS, 1 s segments, 500 ms parts. Viewers ran with `--low-latency` |
| Observability | Grafana Cloud (box node and MediaMTX metrics from boot, #706), Cloud Run console |

### 2.2 Load generators

The plan called for `c-8` droplets. DigitalOcean refused them with "size restricted, account tier", so both generators were `c-4` (4 vCPU) in BLR1, next to the box. Both were deleted after the test.

| Generator | Role |
|---|---|
| `loadgen-blr1` ("gen1") | Ran `run.mjs`. It handled:<br>- the test host and webinar, seats and cleanup<br>- presenters (headless Chrome, software x264)<br>- screen share<br>- API load<br>- the cloud-recording helper<br>- small viewer counts (5 to 25)<br>- the meeting test |
| `loadgen-blr2` ("gen2") | Viewers only (`hls-viewers.mjs` with the `keys-extra.json` from gen1), 4 worker processes |

### 2.3 What each simulated viewer does

Each viewer follows the browser's path:

1. Join with a seat key.
2. Hold the SSE event stream open.
3. Load the chat, questions and polls backlogs.
4. Send a beat every 30 s.
5. Play LL-HLS with blocking playlist reloads and every part fetched once.

It does not decode video. A playback model turns part arrival times into:

- **live latency:** wall clock minus the playhead's `PROGRAM-DATE-TIME`;
- **stalls:** the buffer ran dry for at least 100 ms.

See [LOAD-TESTING.md](../LOAD-TESTING.md#what-one-hls-viewer-does).

### 2.4 Presenters and API load

- **Presenters.** The `host` published a looping 720p30 test pattern. In the logs it is about 2.6 Mbit/s at 1280x720. `panelist2` published 640x360 at about 0.8 Mbit/s. In runs 4 and 5 the host also shared their screen.
- **API load** (runs 2 to 5), per second:
  - 1 chat message
  - 1 poll vote
  - 0.5 joins
  - 0.2 upvotes
  - 0.1 questions

  That is about 2.8 requests/s of interactive traffic on top of the viewers' own beats and event streams.

## 5. Generator limits and how to read the stalls

**Every client-side number in this report was measured by the generator, and the generators were the weakest machines in the test.** These rules decide which numbers to believe.

1. **The kit's own warning.** The kit prints a `WARNING` when event-loop p99 is over 200 ms, or when CPU is over 85% of the processes' cores. It fired in:
   - run 2 step 2 (308 ms);
   - run 3 steps 1 and 2 (261 ms, 820 ms);
   - run 4 on gen1 (268 ms).

   Treat those steps' latencies, stalls and API p95s as generator artefacts.
2. **`playlist 400` is a client symptom.** The origin answers 400 when a blocking reload asks for `_HLS_msn` or `_HLS_part` too far beyond the live edge. That happens only when the client's idea of "now" is late. It appeared in large numbers only when a generator was loaded:
   - 14,054 in run 3 step 2;
   - 781 in run 4 step 3;
   - 829 in run 5.
3. **Same result with and without the CDN.** At 500 viewers, the results through the CDN (run 4) and direct to the box (run 5) were nearly the same:

   | | Run 4 (CDN) | Run 5 (direct) |
   |---|---|---|
   | live50 | 3.0 s | 3.2 s |
   | media95 | 388 ms | 408 ms |
   | stall-time % | 5.5% | 6.7% |

   Yet the box's CPU was 79% in one and 97% in the other. A box-side limit would have hurt run 5 clearly more. What the two runs share is gen2 pulling about 500 Mbit/s at about 290% CPU on 4 cores.
4. **gen2 was below the warning thresholds at 500, but it was close.**
   - Run 4 step 3: loop p99 95 ms, CPU 292% of 400%.
   - Run 5: 101 ms and 291%.

   So the kit did not warn. But at 200 viewers the same machine was clean (182%, 41 ms, 1 stall). The step from 200 to 500 tripled the stalls per viewer-minute, from about 0 to 14–17, while the server count, joins and event streams stayed perfect.
5. **Not all of it is the generator.** Part fetch p95 rose from 112 ms (200 viewers) to 388 ms (500) through the CDN. Live latency rose from 1.3 to 3.0 s. Part of that may be real:
   - The box was at 79% CPU with the compositor and recorder competing.
   - The CDN was passing most traffic through to the origin.

   We cannot separate the two with today's data. The 1,000-viewer plan (section 8) is built to do that: more generators, each below about 250 viewers.

**Rule of thumb for a `c-4` generator.** A clean ceiling is about 200 HLS viewers, or about 2 Chrome presenters with a screen share and nothing else. The 2 presenters ran in software x264 on the generator, so their resolution drops (`limited: cpu`) were the generator too. In run 5, gen1 had only 5 viewers and the host held 720p the whole time.

## 6. Findings and risks, ranked

| # | Severity | Finding | Evidence |
|---|---|---|---|
| 1 | **High** | **The database connection pool is at its limit with no headroom.** Supabase's session pooler has `pool_size` 15. The API uses 3 instances × (4 pool + 1 LISTEN) = 15. Any extra instance, such as a deploy's new revision starting next to the old one or a scale-out during an event, gets `EMAXCONNSESSION` and crash-loops. | Two API deploys after the test failed this way. Production stayed on the previous revision. A fix is in progress: pool idle timeouts, startup retry, and moving to the transaction pooler. |
| 2 | **High** | **One `c-4` box is at its ceiling at about 500 viewers with 2 presenters, screen share and recording.** | 79% CPU through the CDN. 97.4% direct (saturated). No headroom for a third presenter, 1080p, or a traffic spike. |
| 3 | **High** | **The CDN is not taking most of the load off the origin.** | Box egress was about 451 Mbit/s through the CDN, against 566 Mbit/s direct. Without the CDN the box saturates, so it is necessary, but it needs to cache or collapse LL-HLS properly. |
| 4 | Medium | **Live latency roughly doubles from 200 to 500 viewers** (p50 1.3 → 3.0 s, p95 1.4 → 3.8 s). Still inside the "LL under 3–4 s" target, but only just. | Run 4 gen2. Partly generator (section 5), so not yet proven to be server-side. |
| 5 | Medium | **The DigitalOcean account tier blocks `c-8` and up.** This limits the generators now, and would block a bigger video box (`c-8` or `c-16`) if we need one. | "size restricted, account tier" when the plan's `c-8` was created. |
| 6 | Medium | **The cold-start box takes 2 to 4 min, and the kit's presenter wait is 60 s.** In the product the host sees an honest "Starting servers…" message. But if a host joins at the last minute, viewers wait on a cold box. | Run 1a. |
| 7 | Medium | **Observability gaps.**<br>- No per-container CPU (cAdvisor), so we cannot tell which process saturates the box.<br>- Metric series are 18% over the free tier because of API histogram cardinality.<br>- Exact attendee gauges are not deployed yet (#713). | Grafana. |
| 8 | Low | **Meeting at 9 tabs:** 2 silent tabs and 31 s of freezes. | 0% loss, so this is attributed to the generator. Needs a clean rerun to rule out the server. |
| 9 | Low | **Kit and procedure.**<br>- The 90 s `--extra-wait` window was missed in run 4 (gen2 started about 112 s late). The run was still valid because gen2's steps ran on their own clock.<br>- The step-3 summary of run 3 was not recorded.<br>- LOAD-TESTING.md has the wrong MediaMTX metric names. | Logs. |

What went right (keep it this way):

- **0 viewer join failures caused by the server** in about 1,780 joins (1,480 with client data).
- **The server's viewer count matched the clients exactly** at every peak (50, 200, 500, 525, 505). Beats and event streams were never dropped.
- **0 API 5xx.**
- **The interactive load ran alongside 500 viewers without errors:** chat, votes, questions, joins.
- **Presenter publishing from the box side was stable.** Every resolution drop was the generator's CPU.
- **Cleanup removed every test webinar, host and extra account.**

## 7. Recommendations

**Before any big event (over 200 viewers):**

1. **Fix database pooling.** This is the top priority.
   - Move the API to Supabase's **transaction** pooler, or raise the session pool.
   - Add pool idle timeouts and a startup retry with backoff, so a new instance waits instead of crash-looping.
   - Size it for `maxScale` plus one deploy overlap: (3 + 3) × 5 connections.
   - Prove it with a deploy during an API-load run.
2. **Keep the CDN mandatory** for edge viewers. Never hand out the origin URL.
3. **Fix the CDN caching** for LL-HLS. Check Bunny's cache-hit ratio and origin requests per second for 12:41–12:44. Make sure parts and segments are cached and blocking playlist requests are collapsed. The target: box egress through the CDN should stay roughly flat as viewers grow.
4. **Pre-warm the box** for scheduled events, so the box is up well before the host joins. Extend the kit's presenter wait to about 5 min while the page says "Starting servers" (`presenter.mjs`, the 60 s `waitFor` for the join button).

**For capacity above 500 viewers, or with recording and screen share as the default:**

5. **Use a bigger box, or split the work.**
   - Option A: go up a size (`c-8`, 8 vCPU) for events that expect over 300 viewers or need recording.
   - Option B: offload the recorder, and if possible the mix compositor, to a second box. The SFU and origin then keep the headroom.
   - Measure first: run the stage with no viewers to get the box's baseline CPU, with and without recording.
6. **Raise the DigitalOcean account tier** so `c-8` and `c-16` droplets are allowed. That serves both generators and a bigger video box.

**Observability:**

7. **Fix cAdvisor on the box** (privileged mode or the right mounts and permissions), so the dashboard shows CPU per container.
8. **Reduce the API metric cardinality** to get back under 10,000 series:
   - drop the instance label (or aggregate before remote-write);
   - use status classes;
   - use fewer buckets;
   - template the routes.
9. **Deploy #713** (exact attendee gauges) and correct the MediaMTX metric names in LOAD-TESTING.md (`paths_readers`, `hls_*`).

**Test kit and process:**

10. Extend the presenter wait for a cold box (see 4). Also have `run.mjs` record whatever it has when a step does not close (run 3 step 3).
11. Give each generator one job: one for presenters, the others for viewers. Keep each viewer generator at or below about 200–250 viewers on a `c-4`, or about 500 on a `c-8`.
12. Script the second generator's start (for example, an `ssh` or `scp` step in the runbook), so the 90 s window is not missed.
