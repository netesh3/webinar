# Engage v1 — webinar WhatsApp follow-up

Scope is the coach’s flow below and nothing else. The full plan
([PLANS.md](PLANS.md)) is parked.

## The flow

**Before the webinar**

1. Coach schedules a webinar.
2. People register (phone + WhatsApp opt-in).
3. Engage sends a confirmation, then reminders before the start time.

**After the webinar**

1. Webinar ends.
2. Coach sends a feedback message to everyone.
3. Coach sends different messages based on time watched.
4. Coach picks people from a list and sends to them in bulk.
5. Dashboard shows sent / delivered / read.
6. Replies show up in the dashboard; the coach replies from the dashboard or from their phone.

Rules the screens rely on:

- Only opted-in people are messaged; the send button shows the real count.
- Watch buckets come from the same `watchMin` as the Report tab, so counts match.

  inbox’s webinar filter uses the webinar of the last message we sent them.
- People and Messages replace the Contacts nav entry (`/host/crm` redirects to
  `/host?tab=people`).

## Reply from phone

Meta **Coexistence** lets a number stay on the WhatsApp Business app and the
Cloud API together. The coach keeps chatting from their phone, and Engage
still sends templates and sees messages.

- Onboard through Embedded Signup with the coexistence option (existing
  Connect flow gets a “use my existing WhatsApp Business app number” path).
- Subscribe to `smb_message_echoes` so replies typed on the phone appear in the dashboard thread.
- Limits to accept: WhatsApp Business app only (not personal WhatsApp); lower throughput than a pure API number; some features (e.g. groups) stay app-only.

Fallback if coexistence doesn’t fit a coach: the dashboard works on mobile
browsers, and Engage emails the coach when someone replies.

## Runtime (small fix, not River) — done

Two defects that hurt reminders directly, both fixed:

1. **Nothing sent while the service was idle** (Cloud Run scales to zero, CPU only during requests). Now Cloud Scheduler calls `POST /api/internal/tick` every minute (`X-Tick-Secret`, `TICK_SECRET`), and the pass runs inside that request. The service still scales to zero. Reminders are at most about a minute late. Setup: `deploy/cloud-scheduler-tick.sh`. On a dedicated server, a crontab line, or nothing: the in-process 30 s ticker runs anyway.
2. **Double sends with several instances.** Each pass, and each outbox flush (email, WhatsApp), takes a lease row in `sweep_leases` (migration 0051). One runner at a time across instances, and between the sweep and the flush that a registration or approval triggers. A row, not `pg_try_advisory_lock`, because advisory locks do not survive Supabase's transaction pooler; a lease expires by itself if an instance dies mid-pass. River replaces this with the full plan.
